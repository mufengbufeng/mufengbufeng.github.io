热更新系列-09-HybridCLR如何实现热更新

S SuHang · 游戏开发手记

什么是热更新

在用户没有感知或者低感知的情况下，让用户可以不用安装新的安装包实现功能增加或更新。

Mono 本身就可以热更新

Mono 可以在支持 JIT 的平台上执行运行时加载的新 IL，因此具备做 C# 热更新的基础。但是 iOS 等设备因为权限问题，不能依赖 JIT，所以大部分热更新方案都在解决“如何在 iOS 上执行新代码”这个问题。详见为什么无法使用 JIT 在 iOS 上实现热更新。

虚拟机解决方案

为了解决权限问题，可以在代码中添加虚拟机，以解释执行的方式实现热更新能力，例如 xLua、ToLua，以及各种 Python 热更新方案。原理是通过虚拟机在运行时执行热更新代码。

HybridCLR 官方说

HybridCLR 从 Mono 的 mixed mode execution 技术中得到启发，为 Unity 的 IL2CPP 这类 AOT runtime 额外提供 Interpreter 模块，将它们由纯 AOT 运行时改造为“AOT + Interpreter”混合运行方式。

更具体地说，HybridCLR 做了以下几点工作：

  • 实现了一个高效的元数据（DLL）解析库。
  • 改造了元数据管理模块，实现了元数据的动态注册。
  • 实现了一个从 IL 指令集到自定义寄存器指令集的 compiler。
  • 实现了一个高效的寄存器解释器。
  • 额外提供大量 intrinsic（内建）函数，提升解释器性能。

HybridCLR 加了一台能跑 IL 的“虚拟机”

HybridCLR 把解释器编进最终的 App。这样，热更新 DLL 加载后，不是直接交给 CPU 执行，而是交给 HybridCLR：

这里的“寄存器”是解释器内部用来保存参数、局部变量和临时结果的数据位置，不是说热更新代码直接在 ARM 或 x64 的 CPU 寄存器里运行。

真正被 CPU 执行的，仍然是已经编译进 App 的 C++ 解释器。它负责读取热更新方法的指令，并完成加法、分支、创建对象、调用方法、抛异常这些动作。

本文讲的是最常见的“单独热更新 DLL”路径。HybridCLR 的 Hybrid 指的是 AOT + Interpreter，不是 AOT + JIT。它还有差分混合执行（DHE）等能力，可以让未改动的函数继续使用已有 AOT 代码，但新增或改动的函数仍然不是运行时 JIT 出来的。

桥接函数可以理解成翻译。它把解释器里的参数翻译成 AOT 函数能接收的形式，调用结束后再把返回值翻译回来。

反过来也一样。AOT 代码通过接口、虚函数或 delegate 回调热更新方法时，也需要通过桥接函数把 AOT 侧的参数送进解释器。

桥接函数不是运行时临时生成的。打包前执行 HybridCLR/Generate/All 时，工具会分析程序集，为需要的函数签名生成 C++ 桥接代码，并随 Player 一起编译进去。映射到同一个 HybridCLR 桥接签名的方法可以复用同一个桥接函数；签名会考虑参数、返回值和结构体等 ABI 相关信息，不是只看方法名。这样也满足 iOS 不能在运行时生成代码的限制。

元数据补充解决的是什么问题

泛型是 HybridCLR 里最容易让人困惑的一部分。

假设主工程只在打包时用过 List<int>，后来热更新代码需要调用 List<HotUpdateStruct>。如果这个调用已经有对应的 AOT 实例，或者能命中 IL2CPP 的泛型共享，当然可以直接使用已有 AOT 代码。真正的问题是两者都没有命中时：IL2CPP 可以知道 List<T> 这个类型长什么样，但它没有提前生成 List<HotUpdateStruct> 的成员函数机器码。因为在 IL2CPP 的 IL -> C++ 过程中，原始的泛型方法体 IL 已经被丢掉了，运行时也无法凭空补出来。

HybridCLR 的补充元数据做的事情不是“再生成一份 C++ 代码”，而是把 AOT 程序集中丢失的原始泛型方法 IL 补回运行时。这样，缺少 AOT 实现的那部分泛型方法可以交给解释器执行。

运行时通过 HybridCLR.RuntimeApi.LoadMetadataForAOTAssembly 加载补充元数据。要补的是泛型方法定义所在的 AOT DLL，例如 List<T>.Add 的问题通常应补 mscorlib.dll 或对应基础库的元数据，不是去补 HotUpdateStruct 所在的 DLL。

补充元数据需要和当前主包、目标平台匹配，并且应在执行会用到 AOT 泛型的热更新逻辑之前加载。它会带来额外内存占用，所以性能敏感或常用的泛型实例，仍然值得提前让 AOT 主工程显式引用。AOTGenericReference 生成工具可以扫描并提示这些引用；它生成的是建议清单，仍需要把选定的引用显式放进 AOT 代码，才能让 IL2CPP 在打包时实例化。

官方对这个问题的完整说明在这里：AOT 泛型与补充元数据。

Reverse P/Invoke 又是做什么的

它和普通的 MethodBridge 不是一件事。

MethodBridge 主要解决解释器和 AOT 代码之间的互相调用。Reverse P/Invoke 解决的是：原生 C/C++、Lua 等外部代码拿到一个函数指针后，怎样反过来调用热更新 C# 静态方法。

这类方法通常使用 [MonoPInvokeCallback] 标记。因为 iOS 不能在运行时生成新的 Wrapper，HybridCLR 需要在打包时预留足够数量、且签名匹配的 Reverse P/Invoke Wrapper。为未来可能新增的热更新回调预留数量时，要使用 [ReversePInvokeWrapperGeneration(n)]。普通的热更新代码调用 Debug.Log 并不需要走这条路。

还要注意，这条热更新回调路径目前不会自动封送 string 等复杂参数。参数涉及字符串时，通常要改用 IntPtr 后自行转换，或者把原生回调先放在 AOT 代码中处理。

官方说明：MonoPInvokeCallback 支持。

CLRMethod 容易和 HybridCLR 混在一起

如果你在热更新文章或代码里看到 CLRMethod、CLR 重定向、CLR 绑定，大多数时候说的是 ILRuntime 的类型和机制，例如 ILRuntime.CLR.Method.CLRMethod。

HybridCLR 的核心不是让开发者手写 CLRMethod 重定向，而是扩展 IL2CPP 运行时，让它能加载程序集、解释执行 IL，并用 MethodBridge 处理解释器和 AOT 代码之间的调用。因此在学习 HybridCLR 时，先抓住下面四件事就够了：

  • 在本文讨论的常规路径里，热更新 DLL 中新增或改动的 IL 由解释器执行。
  • 热更新代码调用 Unity API 或主工程代码时，使用 MethodBridge。
  • AOT 泛型缺少方法实现时，使用补充元数据把原始 IL 交给解释器。
  • 原生代码要通过函数指针回调热更新静态方法时，才需要 Reverse P/Invoke Wrapper。

串起来看整个流程

总结：HybridCLR 没有在 iOS 上偷偷做 JIT。它把解释器和一批提前编译好的桥接函数放进 IL2CPP Player 中，让新增 DLL 的 IL 可以被解释执行，同时又能和已经 AOT 的 Unity API、主工程代码正常互相调用。
